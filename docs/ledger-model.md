# Single-ledger accounting model

## Decision

The first version uses one TigerBeetle ledger and four account classes:

| Code | Account class | Accounting type | Normal balance | TigerBeetle invariant |
|---:|---|---|---|---|
| 1001 | Safeguarded cash | Asset | Debit | `credits_must_not_exceed_debits` |
| 2001 | Corporate wallet | Client liability | Credit | `debits_must_not_exceed_credits` |
| 2002 | Card wallet | Allocated client liability | Credit | `debits_must_not_exceed_credits` |
| 2003 | Card-settlement payable | Settlement liability | Credit | `debits_must_not_exceed_credits` |

TigerBeetle ledger `1` represents USD, with every amount expressed in integer cents. The
TigerBeetle `ledger` field identifies the asset being counted; it is not an accounting general
ledger account and it is not a transaction journal.

Every public account ID is generated by the caller with TigerBeetle's time-based ID algorithm
before account creation and is stored directly as `Account.id`. The API has no separate external
account identity and does not hash business identifiers into ledger IDs. This makes account
creation retry-safe without another database: an identical retry returns `exists`, while the same
ID with a different immutable account definition is an idempotency conflict. Account IDs `1` and
`2` are reserved for safeguarded cash and the card-settlement payable.

## Corporate wallet and card wallets

A confirmed bank transfer credits the corporate wallet. Finance then allocates funds to a
specific physical or virtual card with a posted transfer from the corporate wallet to that
card's wallet. Returning or expiring an unused allocation posts the reverse transfer. Money is
never copied: the corporate wallet contains unallocated funds, while each card wallet contains
only the funds assigned to that card.

Each card wallet's `Account.user_data_128` is its immutable parent corporate-wallet ID. The card
service remains responsible for its operational `card_id -> card ledger account ID` mapping and
passes the ledger account ID to this API as `card_id`. We do not discover cards with
`QueryAccounts`: user data is not unique, and the Query API is not the authoritative card
registry.

Daily, monthly, one-time, category, schedule, and geographic limits are authorization policy.
They can reduce what the card may spend below its ledger available balance, but they do not move
money and therefore are not represented as TigerBeetle balances.

## Why there is no authorization-hold account

TigerBeetle pending transfers already maintain `debits_pending` and `credits_pending`. For an
authorization, the card wallet is debited pending and the card-settlement payable is credited
pending. The card's spendable balance is reduced immediately, while the settlement obligation is
not posted until capture.

Adding a generic hold account would duplicate this native state. The settlement payable is not a
hold account: it is the issuing side's actual counterparty account for amounts owed through the
card network, processor, or sponsor bank after capture.

`merchant_id` is transaction and risk metadata, not a ledger account. Darb does not owe every
merchant directly in an open-loop card flow; the merchant is paid on the acquiring side. A stable
96-bit fingerprint of `merchant_id` occupies `Transfer.user_data_64` and `user_data_32`, so reuse
of an approved authorization ID with a different merchant is rejected as an idempotency conflict.
This service emits the original value in its structured transaction log; the wider card platform
owns its durable card-transaction and risk-decision record.

Control accounts are also unnecessary for these operations. They are useful for TigerBeetle's
balance-conditional and balancing-transfer recipes, where a linked chain must test a dynamic
condition that cannot be represented by a permanent account flag.

## Transfer journal

| Operation | Debit | Credit | Mode | Code |
|---|---|---|---|---:|
| Confirmed bank top-up | Safeguarded cash | Corporate wallet | Posted | 1001 |
| Confirmed cash-out | Corporate wallet | Safeguarded cash | Posted | 1002 |
| Allocate to card | Corporate wallet | Card wallet | Posted | 1201 |
| Return from card | Card wallet | Corporate wallet | Posted | 1202 |
| Authorization | Card wallet | Card-settlement payable | Pending | 1101 |
| Authorization increment | Card wallet | Card-settlement payable | Pending | 1102 |

Top-up and withdrawal are confirmed booking commands. A top-up is called only after external funds
are confirmed in the safeguarding account, and a withdrawal is called only after the external
payout settlement is confirmed.
If this service later owns payment-rail initiation, it must first introduce explicit funding
receivable and withdrawal payable accounts rather than changing these commands silently.

## Authorization lifecycle

An initial authorization is a pending transfer. Its transfer ID is also the public
`authorization_id`, and it is stored in `user_data_128` as the authorization group identifier.

Each increment is a separate pending transfer for only the increment amount. It uses the same
debit and credit accounts and the same authorization group identifier. This mirrors the immutable
nature of TigerBeetle transfers and lets the account invariant atomically reject an increment
that would overspend the card wallet.

The increment's relative timeout is derived from the original authorization's absolute expiry.
That value naturally decreases between retries. If TigerBeetle reports only a timeout difference
for an existing increment ID, the service looks up the existing transfer and accepts it only when
every caller-controlled and accounting field matches. This preserves retry safety without
extending the original hold.

Capture and void are the next lifecycle milestone. They will resolve every pending transfer in
the authorization group, using a linked chain when all holds must resolve atomically.

## TigerBeetle-native idempotency

The API `request_id` is the TigerBeetle `Transfer.id`. It is a non-zero 128-bit hexadecimal
identifier and is globally unique across transfer operations in the cluster.

There is no application idempotency database:

1. Submit the transfer synchronously through the shared TigerBeetle client.
2. Treat `created` and an identical `exists` as the same successful economic outcome.
3. Treat `exists_with_different_*` as an idempotency conflict.
4. Treat `id_already_failed` as the deterministic replay of a previously rejected attempt.

If the process stops before returning the result, the caller repeats the same command with the
same ID. Regardless of whether the old or new client session reaches the cluster first, only one
economic event can be created. PostgreSQL or another control-plane database may still be used by
a wider platform for card metadata, risk cases, or external payment workflows, but it is not part
of the ledger consistency boundary.

A request declined before any transfer exists does not create a TigerBeetle object because it is
not a financial event. It is deterministic while this challenge's threshold configuration is
unchanged. Existing approvals remain authoritative across policy changes, but a real risk
platform needs a durable decision record if decline replay must also remain stable across model
or policy changes.
